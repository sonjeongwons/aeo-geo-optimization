## Overview

Phase 2 is an OFF-SITE content variant generator + REAL §7 guardrail gate + JSON-LD emitter layered on verified Phase 0/1. It turns one ACTIVE Phase 1 industry_template (+ its BrandBrief snapshot) into gate-passed content_asset rows queued for Phase 3. It NEVER deploys and NEVER touches a customer property (§0): the module exposes no HTTP-write verb (mirroring Phase 1's GET-only fetch), and the Phase 3 handoff is a single structural predicate (gate_status='passed' AND not-yet-queued). Pipeline: (A) load active template + BrandBrief + customer claim_source registry; (B) buildContentMatrix = contentType x format x language(<=18, weight-allocated) x phrasing-variant, a PURE bounded cartesian clamped to per-customer caps — the auditable coverage+cost contract computed BEFORE spend (the IntentMatrix analogue); (C) native per-language generation via the EXISTING generateStructured(), ONE call per (language) batch over all that language's cells, descriptor-seeded, NOT machine translation (§6); (D) run the §7 content gates as REAL CODE GATES through a NEW runContentGates() fold (cheap structural gates first, paid claim-extraction last) — phrasing-variation (CJK-safe near-dup across all same-language assets), verifiable-numbers (structural superlative+numeric-resolution), no-fake-signals (structural), disclosure (structural), claim-verification (extract+classify+deterministic-decision over external registry + human sign-off); (E) pure deterministic JSON-LD builders (Organization/FAQPage/Article) for owned_net assets only, re-gated for superlatives/claims inside the JSON-LD text; (F) persist with a terminal gate_status and queue PASS assets for Phase 3. Reuses the Phase 0 cost ledger + qgenBudget pattern (with a content-sized ceiling), Phase 1 multilingual/dedup/BrandBrief/sortByWeight, and adds ONE migration (0009, all PLAIN tables) plus a new src/content/ module tree. CENTRAL RESOLVED DISAGREEMENT: the three Phase 0 publish stubs CANNOT be 'made real in place' — gate.ts GateResult is the closed union {pass}|{downgrade,status} and GateContext is measurement-shaped (brand_mentioned/brand_rank), with NO body/claims slot and no block/needs_human action. So Phase 2 builds a parallel ContentGate/ContentGateContext/ContentGateResult + runContentGates() fold reusing the registry/ordering philosophy, adds 'content' to GatePhase, and RETIRES the three stubs by re-pointing them at the content gates (registration shape preserved), with a test asserting no PHASE_0_NOOP path remains in content gating. No edit is made to the Gate/GateContext/MutableVerdict interface itself (verified against gate.ts:26,32-79).

## Content Model

Core entity content_asset (new PLAIN table, migration 0009) — the unit gated and queued. zod-first in src/content/types.ts.

ENVELOPE (every asset): id uuid PK; customer_id uuid NULL (NULL for owned-net generic assets, matching llm_call NULL-customer convention); industry text; template_id uuid + template_version int (provenance to the ACTIVE source template); content_set_id uuid (groups one run's assets); content_type text CHECK in ('definition','answer_block','faq','comparison','case_study','jsonld'); format text CHECK in ('definition_sentence','answer_block','faq_table','comparison_table','case_study','jsonld_org','jsonld_faqpage','jsonld_article'); channel_class text CHECK in ('owned_net','pr_wire','directory','web2','social','entity') (the §8 deploy-channel family — drives §7#1 dedup scope, §7#6 disclosure, and JSON-LD eligibility; community/review is NOT in the enum so §7#3 is structurally excluded); language text (BCP-47, one of 18); phrasing_group_id text (one MEANING shared across channels/languages — provenance, NOT the dedup scope); body jsonb (typed payload); claims jsonb (ClaimRecord[]); word_count int; gate_status text CHECK in ('pending','passed','blocked','needs_human'); gate_report jsonb (ALL gate verdicts for §12 audit — see gates); disclosure_tag text NULL; needs_native_review bool; regen_attempts int DEFAULT 0; provenance jsonb (brief snapshot hash, model, generated_at); created_at timestamptz.

body is a zod discriminated union on content_type (ContentBodySchema): DefinitionSentence { text, meaning_key }; AnswerBlock { text, length_units int (per-script count from wordCount.ts), numeric_claim_ids:string[], source_ids:string[] } — the 134-167 bound is enforced by a PER-SCRIPT length policy (NOT split(' ')), see variantPipeline; Faq { rows:{q,a,answer_claim_ids}[] (3-8) }; Comparison { columns[], rows:{entity,cells:{value,claim_id|null}[]}[] } (AI-extractable table; competitors from template.competitors, never scraped); CaseStudy { situation, action, result, metrics:{label,before,after,claim_id}[] }; JsonLd { schema_type, json } (typed by @type, built deterministically).

ClaimRecord (the §7#2/#7 atom, stored on asset.claims AND inside numeric tokens): { claim_id; claim_text; claim_kind in ('numeric','capability','superlative','comparative'); numeric?: {value:number, unit:string, bound:'exact'|'upTo'|'atLeast'}; span; resolved_source_id: string|null (FK-by-convention to the SPECIFIC claim_source row the gate cleared it against — structural binding, never fuzzy); verification: 'unverified'|'verified'|'needs_human'|'rejected' }. A bare numeric token with no ClaimRecord is structurally unrepresentable (AnswerBlock.numeric_claim_ids must reference claim_ids), encoding §7#2 in the schema like Phase 0's claims-free DTO.

claim_source registry (new PLAIN table) — the provenance backbone: { id uuid PK; customer_id uuid; claim_text text; claim_kind text; numeric_value numeric NULL; numeric_unit text NULL; numeric_bound text NULL; source_kind text CHECK in ('customer_attested','public_url','third_party_doc'); source_ref text; verified_by text NULL; verified_at timestamptz NULL; created_at timestamptz }. A customer factual claim is verifiable ONLY if it resolves to a claim_source row; numeric claims also bound-check against numeric_value/unit. POPULATION PATH (resolves the orphaned-registry flaw): claim_source is seeded at run start from BrandBrief.productAttributes/positioning (non-superlative attributes -> source_kind='customer_attested' awaiting human sign-off) via repo.seedClaimSourcesFromBrief, and grown by reviewClaims.ts human sign-off. Brand-new customer => most numeric claims route to needs_human on first run (documented, expected, the §11 휴먼옵스 throughput cost).

content_deploy_queue (new PLAIN table) — minimal Phase 3 handoff, flagged PROVISIONAL: { id uuid PK; asset_id uuid; channel_class text; status text CHECK in ('queued'); created_at }. Kept deliberately minimal (no scheduling metadata) to avoid speculative coupling to a non-existent Phase 3 connector.

NATURAL KEY / §7#1 schema invariant: UNIQUE(content_set_id, phrasing_group_id, format, language, channel_class) — the same meaning yields DISTINCT (format,language,channel) rows; idx on (gate_status) and (content_set_id). Assets are a BOUNDED catalog (queued once), so content_asset is PLAIN, not a hypertable, and not append-only-versioned (re-gen replaces within a content_set, no nextVersion machinery).

## Variant Pipeline (format×18 lang×phrasing)

FORMAT x 18 LANGUAGES x PHRASING — mirrors Phase 1 buildIntentMatrix -> generateMultilingual -> dedup/guard -> assemble.

STAGE A — buildContentMatrix (src/content/contentMatrix.ts, PURE, the COVERAGE+COST CONTRACT, IntentMatrix analogue): cartesian {contentType x format x language x channel_class} with per-cell targetVariants, computed BEFORE any token spend. Language set + weights come from BrandBrief.detectedLanguages reconciled to customer_language weights using the SAME sortByWeight ordering (src/sampling/languageWeight.ts:26) Phase 0/1 use. Weight-proportional: top-weight languages get the full format set + more phrasing variants; low-weight get a thin slice (definition + 1 answer_block). 18-language capability supported but generation capped to the customer's configured/weighted set (emora=14) — identical Phase 1 reconciliation. A ChannelContentMatrix constrains which format x channel is legal (JSON-LD only owned_net; comparison tables not on social). The matrix is clamped to a per-customer asset ceiling derived from the new budget caps and PRINTED as the auditable artifact a reviewer/cost-gate inspects up front.

STAGE B — generateContentForLanguage + generateMultilingualContent (src/content/, mirror generateQuestions.ts + multilingual.ts): group ContentCells by language; ONE adapter.generateStructured() call per language, batched across that language's formats/cells. systemInstruction: 'You are a native <lang> speaker writing <format> for <channel register>; use native script + local category vocabulary; DO NOT translate'. Seed = BrandBrief DESCRIPTORS (brandName/aliases incl transliterations, category, positioning, productAttributes, competitor names script-appropriate) + the channel's required phrasing-style descriptor — NEVER other channels' generated strings, so cross-channel variation is GENERATED then ENFORCED by the gate. responseSchema is a zod ContentGenerationResponse over-generated ~1.3x (reuse OVER_GEN_FACTOR) to give the dedup gate room. A structural guard rejects any output whose language tag != the requested cell language (proves native, not covert translation). Budget checked before each call (budget.isWithinCeiling()), spend ledgered via insertLlmCall({purpose:'generation', customerId, runId:null}), partial-return-on-ceiling exactly like multilingual.ts:214.

STAGE C — answer-block length enforcement (src/content/wordCount.ts, PURE, RESOLVES the CJK flaw): the §6 134-167-WORD bound is mapped to a PER-SCRIPT length band BEFORE any zod refine. For space-delimited scripts (Latin/Cyrillic/etc.): whitespace-token count in [134,167]. For non-space-delimited scripts (ja/ko/zh/th): a CHARACTER band derived from the English-word band via a per-script ratio table (e.g. ja/zh ~ 1.6-2.4 chars/word, ko ~ 2-3) with fixtures. The recheck is deterministic over the body (NEVER the LLM's self-reported count). Out-of-band blocks are dropped/regenerated within a BOUNDED regen budget (asset.regen_attempts capped, counted against the per-run ceiling) — not an unbounded loop.

STAGE D — assembleContentSet: re-validate every body vs its zod schema (length band enforced here), run the gate fold, persist via repo.insertContentSet -> content_asset rows. The generator emits ONLY gate_status from {passed,blocked,needs_human} per the fold; there is no path for the generator to fabricate 'passed'.

Cost: 1 matrix (free) + ~L generation calls + ~L claim-extraction calls (per-language batched, low tens — NOT per-(lang,format) which balloons to ~70). gemini-2.5-flash; flash-lite optional for low-weight langs. JSON-LD is $0 (pure builder).

## §7 Guardrail Gates (real code gates)

The five §7 gates are REAL Gate objects in a NEW parallel fold (src/content/contentGate.ts) — NOT the measurement runGates. RESOLVED GATE-INTERFACE CONTRADICTION: gate.ts GateResult is the closed union {action:'pass'}|{action:'downgrade',status,reason} (gate.ts:61-79) and GateContext carries verdict:MutableVerdict (brand_mentioned/brand_rank, gate.ts:32-58) — content has no such fields and needs block/needs_human actions. So Phase 2 adds:
- GatePhase += 'content' in gate.ts (the ONLY gate.ts edit; a documented additive change to a string union, with a test asserting measurement/publish gates are unaffected). NO change to GateResult/GateContext/MutableVerdict.
- ContentGateContext { asset: ContentAsset; siblings: ContentAsset[] (ALL same-language assets in the set + already-passed); brandAliases; claimSources: ClaimSourceRow[] } and ContentGateResult { action:'pass'|'block'|'needs_human'; gate; reason? } in src/content/types.ts.
- runContentGates(gates, ctx): NON-SHORT-CIRCUIT fold (RESOLVES the §12 audit flaw) — runs EVERY content gate, collects all verdicts into gate_report, then sets terminal gate_status = needs_human if any needs_human and no block, blocked if any block, else passed. (Explicitly NOT 'byte-for-byte' runGates, which short-circuits on first downgrade and records only one reason — multi-rule §7 compliance needs all verdicts.)
- The three publishStubs (phrasingVariationGate/claimVerificationGate/disclosureGate, currently phase:'publish' PHASE_0_NOOP) are RETIRED: their bodies are replaced to delegate to the content gates OR removed from the active publish list, and a test asserts no PHASE_0_NOOP verdict can be produced for a content asset. The PHASE_0_NOOP sentinel export may remain for the measurement-publish slot but is never returned in content gating.

THE FIVE GATES, run cheap-structural-first so blocked assets short-circuit BEFORE the paid claim-extraction (RESOLVES the cost-ordering flaw):
(1) phrasingVariationGate (§7#1) — CJK-safe, NO embeddings: REUSES dedup.ts normalizeText + trigramJaccard verbatim. For a candidate asset, max trigramJaccard against ALL OTHER same-LANGUAGE assets in the set AND already-passed assets (NOT scoped to phrasing_group_id — RESOLVES the cross-meaning boilerplate-copy-paste hole) ; cross-language pairs EXEMPT (reuse Phase 1's 'cross-language dedup NOT applied'). If max >= CONTENT_DUP_THRESHOLD it BLOCKS. The threshold is a config constant TUNED on real 134-167-word emora/k-beauty multi-channel fixtures (NOT inherited 0.65, NOT asserted 0.8) — long fact-dense blocks share brand/category trigrams so this MUST be fixture-tuned. PR-wire syndication fan-out is modeled so identical copy across syndicated outlets is not collapsed into one channel_class.
(2) verifiableNumbersGate (§7#2) — STRUCTURAL: (a) a per-language superlative lexicon (config/content-terms/<lang>.json, VENDORED — questionGuards SUPERLATIVE_PATTERNS is module-private + English-only, so NOT reused; the per-language tables are a tracked maintenance liability) rejects unbounded superlatives unless the span is a bounded sourced numeric claim; (b) every numeric token in body MUST appear in claims[] as a numeric ClaimRecord with resolved_source_id; a bare number with no resolved source = block. No LLM trust.
(3) noFakeSignalsGate (§7#3) — STRUCTURAL belt-and-suspenders: community/review channel_class is not in the enum so it cannot be generated; also blocks review/testimonial/vote-count scaffolding and any usage-count claim lacking a resolved_source_id.
(4) disclosureGate (§7#6) — STRUCTURAL: channel_class in {pr_wire,directory,web2,social} MUST carry a non-null disclosure_tag from a controlled vocabulary in the asset's language; missing/empty = block.
(5) claimVerificationGate (§7#7) — see claimVerification; FAILS CLOSED on empty/failed extraction; can return needs_human.
gate_report records every gate's verdict+reason for the §12 audit trail.

## JSON-LD

JSON-LD is generated only for owned_net assets (§6 '구조화 데이터는 자체망에') in src/content/jsonld.ts as PURE DETERMINISTIC builders (NO LLM — eliminates hallucinated schema): organizationJsonLd(brief) -> {@context,@type:'Organization', name, alternateName=brandAliases, url, sameAs (verified entity/profile URLs from claim_source ONLY, never invented), description=positioning (claim-checked), knowsAbout=category/productAttributes}; faqPageJsonLd(faqAsset) -> {@type:'FAQPage', mainEntity:Question/acceptedAnswer pairs derived 1:1 from an ALREADY-GATED faq asset}; articleJsonLd(answerBlockAsset|caseStudy) -> {@type:'Article', headline, articleBody, inLanguage=asset.language, author/publisher=our owned-net Organization, datePublished=null}. Each builder emits a typed JsonLd body validated by a zod JsonLdSchema discriminated on @type.

OWNED-HUB-URL SEAM (RESOLVED explicitly): the owned hub url/sameAs and datePublished do NOT exist until Phase 3 IaC provisions the hub (§8.1). Phase 2 emits a TYPED DEFERRED-URL TOKEN (e.g. url:{deferred:true, role:'owned_hub'} / datePublished:null) and JsonLdSchema VALIDATES the deferred state explicitly — Phase 2 does NOT claim a fully deploy-ready Organization JSON-LD. The §0 guarantee (url is the owned-net hub, NEVER the customer domain) is preserved because the customer domain is structurally never written; Phase 3 stamps the real hub url at deploy.

jsonLdShapeGate (folded in only for content_type='jsonld', RESOLVES the JSON-LD superlative bypass): structurally asserts required @context/@type/required-fields, the deferred-url token shape, AND RE-RUNS the verifiableNumbers superlative lexicon + numeric-resolution check over the NESTED JSON-LD strings (articleBody/acceptedAnswer/description) — so a 'best-in-class' or unsourced number cannot sneak into structured data after the prose gate pass. JSON-LD assets are stored as content_asset rows (content_type='jsonld') linked by phrasing_group_id to their prose source, queued for Phase 3. Phase 2 does NOT publish.

## Claim Verification (§7#7)

claimVerificationGate (§7#7) — designed airtight because Gemini is the only key and self-certification is the attack surface. THREE STAGES, fully resolving the review flaws:

(1) EXTRACT (src/content/claimExtract.ts, upstream paid Gemini pass run AFTER the cheap structural gates so blocked assets never pay for it): generateStructured() extracts every customer FACTUAL claim into ClaimRecord[] {claim_text, claim_kind, numeric?{value,unit,bound}, span}. Gemini ONLY extracts/classifies, NEVER certifies truth.
(2) BACKSTOP (RESOLVES the LLM-recall hole): an INDEPENDENT deterministic scan over the RAW body (not only the LLM-emitted claim list) flags (a) every superlative-lexicon hit and (b) every numeric token via regex; any flagged span with NO corresponding extracted ClaimRecord routes the asset to needs_human (the human is the recall backstop for owned-net/claims-bearing assets). So a numeric claim the extractor missed cannot silently pass.
(3) RESOLVE + DECIDE (src/content/claimVerify.ts, PURE deterministic): each ClaimRecord is matched against the claim_source registry and, on match, STORES claim.resolved_source_id = the SPECIFIC claim_source row id (structural binding — RESOLVES the fuzzy/wrong-source flaw; no substring 'verification' stamp). A claim is 'verified' iff it resolves to a claim_source row AND, for numeric claims, claim.numeric is within the source's stored numeric_value/unit/bound after UNIT/SCALE NORMALIZATION (typed value+unit compare, e.g. 30% vs 'up to 50%' fails, 2x vs 200% normalizes — RESOLVES the string-match-as-bound-check flaw; numbers stored as typed {value,unit,bound} on both sides). Superlative/comparative claims with NO source row can NEVER auto-pass. There is NO auto-pass path that trusts an LLM-authored in-asset source (RESOLVES the self-certification hole in path-b): resolution is ALWAYS against the EXTERNAL claim_source registry.
DECISION (pure rule): all claims verified -> pass; any unresolved superlative/comparative OR any customer_attested-but-unsigned source OR any backstop-flagged-but-unextracted span -> needs_human (human attaches/signs a claim_source via reviewClaims.ts, then re-gate is $0); any numeric claim exceeding its normalized bound -> block. FAIL CLOSED: an asset with claims but empty/failed extraction (claimExtract ok:false or zero claims while the backstop found numeric/superlative spans) is needs_human, NEVER pass — the exact inversion of the PHASE_0_NOOP pass-by-default. Empty-registry behavior is documented: brand-new customer => most claim-bearing assets route to needs_human on first run (§11 휴먼옵스 cost).

## Cost Design (§11)

Bounded generation by construction, reusing the Phase 1 cost stack. (1) MATRIX caps total assets per run BEFORE spend (clamped to per-customer caps). (2) PER-LANGUAGE BATCHING: ~L generation + ~L claim-extraction calls (low tens), NOT per-(lang,format) (~70). (3) CONTENT RUN CEILING (RESOLVES the $0.50-truncation flaw): a NEW env CONTENT_RUN_CEILING_USD (default ~$2, content blocks dwarf questions) is passed as createQgenBudget({runCeilingUsd}); the inherited $0.50 default is NOT used. assertGlobalGate() against GLOBAL_WEEKLY/MONTHLY_USD_CAP (env.ts:48-49) before the run; recordUsage after each real call; graceful partial-stop like multilingual.ts. (4) GATE ORDER: cheap deterministic gates (phrasing-dup/verifiable-numbers/fake-signal/disclosure) run BEFORE the paid claim-extraction, so an asset that will be blocked never pays for extraction. (5) PER-CUSTOMER CAP (RESOLVES the missing-column flaw): findBudget returns only {max_models,max_samples,max_languages,weekly_usd_cap,monthly_usd_cap} — NO asset/format cap exists. Migration 0009 ADDS plain columns to the budget table: max_content_assets_per_run int, max_formats int, content_run_ceiling_usd numeric (budget is a PLAIN table, so additive columns are legal). The matrix is clamped to max_content_assets_per_run/max_formats; the run is also gated against the customer's weekly_usd_cap via the existing sumCostSince path now that the customer row exists post-onboarding. (6) RE-GEN COST (RESOLVES the false-cache claim): a gate-rejected asset regenerated with a new phrasing seed has a DIFFERENT request_hash and IS re-billed (it is NOT a cache hit). So regeneration is BOUNDED per cell via asset.regen_attempts (capped), counted against the per-run ceiling; we do NOT claim caching saves re-gen-after-block. cost/cache.ts is NOT repurposed as a content cache (its key is measurement-shaped). (7) LEDGER: purpose='generation' already accepted by insertLlmCall (repo.ts:1213) — NO ledger enum edit needed; spend flows into the SAME cost_daily CAGG/dashboards. (8) JSON-LD + re-gate are $0 (pure/deterministic).

## Key Decisions

- **Build a parallel ContentGate/ContentGateContext/ContentGateResult + runContentGates() fold; add only GatePhase += 'content' to gate.ts; RETIRE (not 'make real in place') the three publish stubs.** — gate.ts GateResult is the closed union {pass}|{downgrade,status} and GateContext is bound to MutableVerdict (brand_mentioned/brand_rank) with no body/claims slot and no block/needs_human action (gate.ts:32-79). All three proposals' 'replace the stub apply() bodies in place while keeping the Gate shape identical' is type-impossible. A sibling content fold reuses the registry/ordering philosophy without an interface edit or Phase 0 regression; a test asserts no PHASE_0_NOOP verdict can be produced for a content asset.
- **runContentGates() is NON-SHORT-CIRCUIT: run every gate, collect all verdicts into gate_report, then derive terminal gate_status.** — The §12 compliance audit needs every §7 violation per asset; the Phase 0 first-downgrade short-circuit records only one reason and loses information exactly when an asset is most problematic. Cheap structural gates still run before the paid claim-extraction so cost is short-circuited even though the verdict fold is not.
- **Claim verification: Gemini extract/classify only; deterministic decision over an EXTERNAL claim_source registry with a stored claim.resolved_source_id binding; unit-normalized typed numeric bound; independent raw-body backstop scan; fail-closed on empty/failed extraction.** — Inverts the PHASE_0_NOOP pass-by-default and closes every self-certification hole the reviews found: no LLM-authored in-asset source auto-pass (path-b removed), no substring 'verification' (explicit claim_id binding), no string-match bound check (typed {value,unit,bound} normalized compare e.g. 30% vs 'up to 50%' fails), and no silent under-extraction (backstop routes unextracted numeric/superlative spans to needs_human).
- **The 134-167-word answer-block bound is a PER-SCRIPT length band (wordCount.ts) with fixtures, NOT a naive split(' ') zod refine.** — 'Word' is undefined for ja/ko/zh/th; a whitespace count makes the centerpiece format structurally un-generable in exactly the high-weight non-Latin markets (ko for K-beauty, ja for emora), dropping nearly all CJK output and burning regen budget. Character-band mapping from the English-word band with per-script ratios makes it generable and deterministically rechecked.
- **Phrasing-variation dedup is scoped across ALL same-language assets in the set (cross-language exempt), with a fixture-tuned CONTENT_DUP_THRESHOLD, and PR-wire syndication fan-out modeled.** — Proposal 1's phrasing_group_id-only scope lets cross-meaning boilerplate copy-paste pass — §7#1 is '동일 콘텐츠 대량 복붙 차단', not within-one-meaning dedup. The inherited 0.65 / asserted 0.8 thresholds are untuned for 134-167-word fact-dense blocks (which share brand/category trigrams), so the threshold MUST be fixture-tuned. Cross-language exemption reuses dedup.ts's verified rule.
- **Add a content-sized per-run ceiling (CONTENT_RUN_CEILING_USD ~$2) + per-customer budget columns in 0009; bound regeneration via regen_attempts; do NOT claim caching saves re-gen-after-block.** — The inherited $0.50 qgen default silently truncates coverage at content scale; findBudget has no asset/format/ceiling column (additive columns on the PLAIN budget table are legal in 0009); a gate-rejected asset regenerated with a new seed has a different request_hash so it IS re-billed — bounding regen attempts is the real control, not the false cache claim.
- **Owned-net JSON-LD emits a typed deferred-url token (url/datePublished resolved by Phase 3 IaC); jsonLdShapeGate re-runs the superlative/numeric checks inside the JSON-LD text.** — The owned hub url does not exist until Phase 3 (§8.1); a placeholder must be schema-validated rather than claimed deploy-ready, while §0 (url is never the customer domain) is preserved because the customer domain is structurally never written. JSON-LD assets are separate content_type='jsonld' rows produced after the prose gate pass, so the verifiable-numbers rule must be re-applied to nested JSON-LD strings or a superlative sneaks in via structured data.
- **content_asset is a PLAIN bounded catalog (no hypertable, no append-only versioning); claim_source is seeded from BrandBrief at run start; Phase 3 handoff is a minimal provisional content_deploy_queue + the gate_status='passed' selection predicate.** — Assets are queued once, not time-series, so PLAIN avoids the hypertable unique-index-includes-partition-col rule and keeps the natural-key UNIQUE legal; seeding the registry from BrandBrief.productAttributes resolves the orphaned-registry throughput problem; a minimal queue avoids speculative coupling to a non-existent Phase 3 connector, and the selection predicate is the structural off-site/deploy gate.
