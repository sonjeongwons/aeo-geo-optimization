# Phase 5 (FINAL) — Customer Dashboard + Weekly Reports + Approval Workflow + Billing — Canonical Design

## Overview

Phase 5 is the FIRST customer-visible surface of the off-site AEO/GEO done-for-you service. It is ADDITIVE: nothing in the verified Phase 0-4 measurement/judge/cost core changes. It adds a Next.js 15 (App Router, React 19, Node 22, TS strict) dashboard at apps/web/ in the SAME repo, importing the backend src/domain/* zod/types VERBATIM (the Phase 0 reason TS was chosen). It wires the SPEC §10 funnel as the product surface: (1) public free-diagnostic widget (entry), (2) weekly SMR auto-report (retention), (3) full dashboard v1-b (SMR trends over time + per-model/per-language/per-competitor breakdown + priority-gap questions). It surfaces the THREE existing approval CLIs (review-template §5.5, review-claims §7, approve-deploy) as in-dashboard human-gate flows that call the IDENTICAL underlying functions, and adds month-to-month/no-lock-in billing (§1) metered from the llm_call ledger (§11). The whole thing is multi-tenant fail-closed.\n\nThe architecture resolves the reviews' must-fixes against the real code: (a) the dashboard reads go through tenant-scoped Next.js Route Handlers/Server Components that call assembleReport()/repo.* AFTER a server-side ownership check (findRun(runId).customer_id === session.customerId; 404 on mismatch — no existence leak); (b) the legacy unauthenticated GET /smr/:runId and POST /diagnose on the Fastify engine are REMOVED from public exposure / bound to internal-only (engine stays runnable for ops, but the customer surface never re-blesses an unscoped route); (c) approval MUTATIONS get NEW customer-keyed repo wrapper variants (signClaimSourceForCustomer, approveDeployRowForCustomer) that load the target row, resolve its owner, and reject when NULL or != session.customerId BEFORE calling the Phase-0 primitive — because signClaimSource(id)/approveDeployRow(assetId) are id-keyed with no customer predicate and content_asset.customer_id is NULLABLE; (d) industry_template review/activate is moved to a STAFF-ONLY surface (industry_template has NO customer_id and activation is industry-global + emits YAML via materialize()); (e) billing separates OUR provider cost (llm_call.usd, USD, tiny today) from customer PRICE via a pure pricing.ts (price ∝ questions×languages) with margin + FX + VAT layered in invoice_line, accounting for NULLABLE llm_call.customer_id; (f) weekly delivery persists an immutable report_snapshot at delivery time (trends read snapshots, not live recompute, so a later re-judge never silently drifts the historical email) with exactly-once delivery; (g) NO RLS on Timescale hypertables/CAGGs — app-layer requireCustomerScope is the primary, tested guard.\n\nVisual system is grounded in the fetched gpto.kr: DARK navy/near-black surfaces with cyan/electric-blue data accents, white tabular numerals, dense document-like data tables — explicitly NOT a light gradient/emoji AI-generated look (the reviews verified gpto.kr is dark-mode). §0 no-results-guarantee and §1 no-lock-in are always-visible, tested UI invariants. New migrations are 0013-0016 (auth/session, billing/subscription, report-delivery, supporting indexes); 0005/0008 are absent in the existing sequence and the next free number is confirmed 0013.

Placement: apps/web/ as a Next.js 15 App Router app (React 19, Node 22, TypeScript strict, RSC). This is documented as an AMENDED Phase-0 decision: DESIGN.md said \"single typed src/ tree (NOT a monorepo)\" to avoid heavy multi-package build tooling — npm workspaces + a tsconfig path alias add ZERO new infra and preserve the single src/ tree as the engine, so the steer's intent (share src/domain verbatim, no Redis, no Temporal) holds. The engine docker image, `docker compose up`, `npm run migrate`, and `npm run diagnose` keep working unchanged.\n\nType-sharing (no duplication): apps/web/tsconfig.json sets \"paths\": { \"@engine/*\": [\"../../src/*\"] }. The dashboard imports domain DTOs DIRECTLY: `import type { RunReport, SMR, Visibility, SoV, SMRDecomposition, PriorityGapQuestion, MetricTuple } from \"@engine/domain/metrics.types\"`; `import type { Run, Customer, LanguageCode, RunStatus } from \"@engine/domain/types\"`; and the SELF_JUDGE_BIAS_DISCLOSURE const is rendered verbatim. domain/* is asserted PURE (header comments confirm no IO/pg/@google/genai), so it tree-shakes cleanly.\n\nBUNDLE BOUNDARY (enforced structurally, not by lint alone — review must-fix): the engine modules that pull pg/kysely/pino (report.ts, repo.ts, kysely.ts, scheduler/*, billing/*, report/*) are marked with React's `import \"server-only\"` at the top of a thin web-side facade (apps/web/lib/engine.server.ts) that re-exports assembleReport + the scoped repo functions. A client-component import of that facade is then a BUILD-TIME error. The ONLY thing allowed to cross into client components is @engine/domain/* (types) — also backstopped by an ESLint no-restricted-imports rule forbidding @engine/db|metrics|providers|scheduler|billing|report in \"use client\" files. Reads/mutations run ONLY in Server Components, Route Handlers, and Server Actions (Node runtime, never Edge).\n\nDate serialization (review must-fix): RunReport.generatedAt and run.finished_at/reviewed_at are JS Date. The web layer never ships a raw Date to a client component. A small DTO transform (toWireReport(report): WireRunReport) in lib/engine.server.ts converts Date→ISO string and is the ONLY shape passed to client charts/tables; WireRunReport is derived from RunReport with Date fields remapped to string, kept in apps/web/lib/wire.ts and shared by server and client.\n\nReads go through assembleReport()/repo read functions; mutations reuse the EXACT functions the CLIs call (actionReviewed/actionActive/actionEdit; signClaimSource+regateAsset; approveDeployRow) wrapped in customer-keyed guards. No raw SQL in the web layer, no second pg pool owner for measurement — the Next.js Node runtime opens its own pool via getDb() ONLY for the additive read/billing/auth tables and the scoped reads, sharing the same Postgres+Timescale; the engine process remains the sole owner of pg-boss and the measurement write path. Charts: Recharts (lightweight, declarative, SSR-friendly, tree-shakeable; no hand-rolled d3).

## Report Automation

Reuse the EXISTING weekly machinery; do not rebuild it. The operating cycle already runs weekly via pg-boss (CYCLE_CRON_QUEUE → cycle.plan → response.run fan-out → cycle.aggregate), and cycle.aggregate already calls assembleReport(runId). Phase 5 adds ONE new job report.deliver plus a render+persist step, with EXACTLY-ONCE delivery (review must-fix).\n\n(1) src/scheduler/jobs.ts: add JOB_NAMES.REPORT_DELIVER = 'report.deliver', a Zod ReportDeliverPayloadSchema { runId: uuid, customerId: uuid }, and DLQ_REPORT_DELIVER = 'report.deliver.dlq'.\n\n(2) Enqueue point: the cycle.aggregate handler enqueues report.deliver ONLY after a successful operating-run aggregate, with singletonKey `report:${runId}` to dedupe across the handler's own retries (cycle.aggregate is retryable — verified in worker.ts). Because aggregate may have already committed before the enqueue (so a crash could MISS a send, not just double-send), delivery is at-least-once + idempotent: the report.deliver handler is the source of truth and the report_delivery UNIQUE(snapshot_id, recipient) backs idempotency; a missed enqueue is recovered by boot catch-up (extended to also enqueue report.deliver for any completed operating run lacking a report_snapshot). Baseline runs do NOT enqueue report.deliver (one-shot, no subscription).\n\n(3) New src/report/deliver.ts (engine side, NOT web): calls the UNCHANGED assembleReport(runId) → RunReport; computes WoW delta by loading the PREVIOUS operating run via a new repo.findPreviousOperatingRun(customerId, beforePlannedAt) that filters kind='operating' AND status='completed' (review must-fix — partial/over_budget runs have a different n_total and would mislead the headline delta); then INSERTs a report_snapshot row { id, customer_id, run_id, week_start (derived from run.finished_at/planned_at — there is no run.week_start column), smr, visibility, top_sov, abstain_rate, wow_smr_delta, report_json (the literal RunReport jsonb), generated_at }. report_json is the immutable as-delivered copy; trend charts and the emailed report render the exact same numbers and never drift on a later re-judge.\n\n(4) Delivery sink: deliver.ts renders an HTML email (a server-rendered template reusing the same DTO) and sends via a pluggable DeliverySink interface (mirrors the existing AlertSink/SecretProvider seam). Phase 5 ships at least ONE real sink (Resend or SMTP adapter) so the §10 retention loop is actually functional end-to-end — a console NoopSink alone is not \"weekly report automation\"; the Noop sink remains the dev default. A report_delivery row { id, snapshot_id, recipient, channel, status (sent/failed), sent_at } logs audit + idempotency; failures dead-letter to DLQ_REPORT_DELIVER and raise an ops alert (never silently dropped).\n\n(5) Timezone: delivery tz is per-customer (default Asia/Seoul, KR-first per gpto framing) via the existing ScheduleJobOptions.tz; missed-window durability is already guaranteed by pg-boss. UI i18n is out of scope (noted limitation). No change to runCycle/aggregate metrics math.

## Billing (§11)

Per §1 (month-to-month, NO lock-in — explicit contrast to GPTO's 6-month minimum, but stated as quiet plan terms, not a comparative marketing jab, to respect §7#2/§0) and §11 (price ∝ questions×languages, heavy-use pass-through). Billing SEPARATES our provider cost from customer price (review must-fix).\n\nPRICE BASE: a pure src/billing/pricing.ts exports priceForScope({ questionCount, languageCount, models, samples }): { baseKrw } — derived from COUNT(active question) × COUNT(customer_language) (the two §11 cost drivers) bucketed into tiers anchored to the §1 ~₩2,000,000/mo VAT-별도 GPTO-parity tier. It is pure + shared so apps/web shows the exact same quote the engine bills. The tier curve and overage multiplier are flagged as BUSINESS INPUTS that must be supplied (the data model supports any curve); Phase 5 ships a default conservative curve + the math.\n\nUSAGE METERING reads the EXISTING llm_call ledger via the cost_daily CAGG (no new metering pipeline). A new repo.sumLlmUsageForPeriod(customerId, periodStart, periodEnd) aggregates the invoicing window from cost_daily. CRITICAL coverage fix: llm_call.customer_id is NULLABLE — Phase-1 onboarding and the public /diagnose spend land in a NULL bucket and would silently escape per-customer metering. Phase 5 explicitly ABSORBS NULL-customer spend as overhead (not billed to any tenant) and documents it; the per-customer invoice only meters non-null rows. Also reconcile the monthly window with cost_daily's 35-day start_offset: the close job reads the prior full month which is inside the CAGG materialization window; any backfill/re-judge older than 35 days is out of scope and noted.\n\nINVOICE MODEL (migration 0014): subscription { customer_id, plan_tier, base_krw, status (trialing/active/paused/canceled), started_at, current_period_start, current_period_end, cancel_at_period_end } and invoice { id, customer_id, period_start, period_end, base_krw, usage_overage_krw, vat_krw, total_krw, status, issued_at } + invoice_line { invoice_id, kind (base/overage/human_ops), label, amount_krw }. invoice_line layers margin on overage, USD→KRW FX, and VAT ('VAT 별도', §1) EXPLICITLY — never billing raw llm_call USD. Human-ops line items (§11) are manual/assumed (quantification is human-entered). A monthly pg-boss billing.close cron (1st of month) sums the window into invoice/invoice_line.\n\nBilling page app/(app)/billing: current plan + base (KRW), this-period usage gauge (USD spent vs cap + cache-hit % as an efficiency/trust signal), question/language/model scope (what they pay for), projected invoice, invoice history, and a prominent \"월단위·무약정 — 언제든 해지\" panel that sets subscription.cancel_at_period_end (access ends at period end, no immediate data loss). A clear caveat restates \"성과(노출) 보장 없음\" (§0) near plan terms. Payment capture is OUT of scope (B2B sales-led invoice, like gpto's ~₩2M/mo motion) behind a pluggable PaymentProvider seam (Stripe/Toss adapter later); Phase 5 ships the data model + invoice generation + manual/CSV export.

## Auth & Multi-tenant

Multi-tenant, fail-closed, app-layer as the PRIMARY guard (NO Timescale RLS — review must-fix).\n\nSCHEMA (migration 0013): app_user { id, email UNIQUE, password_hash, customer_id uuid NULL REFERENCES customer(id), role text CHECK (role IN ('owner','member','staff')), created_at } — customer_id is NULLABLE so internal staff (role='staff', customer_id NULL) who act across customers for ops/templates ARE representable (this fixes Proposal 3's NOT NULL contradiction). app_session { id, user_id REFERENCES app_user(id), token_hash, expires_at, created_at }. pgcrypto is already enabled.\n\nAUTH: email+password (argon2/bcrypt) issuing an httpOnly, Secure, SameSite=Lax cookie holding an opaque token whose SHA-256 hash is stored in app_session. A single getServerSession() helper (apps/web/lib/session.ts) resolves { userId, customerId, role } from the cookie on every Server Component / Route Handler / Server Action. requireCustomerScope() returns the session customerId or fails (302→login if no session; 403 if customer_id NULL and role!='staff'). requireStaff() gates the (staff) console.\n\nENFORCEMENT (the security core): the session customerId is NEVER taken from a client-supplied param. Every web read passes the SESSION customerId into the customer-keyed engine repo functions (findBrandsByCustomer, findCostDailyRows, listReportSnapshots, etc.). For row-id reads (reports/evidence), the handler re-checks ownership before returning: GET /api/reports/[snapshotId] verifies report_snapshot.customer_id === session.customerId; assembleReport(runId) is only called after findRun(runId).customer_id === session.customerId. Non-owned ids return 404 (not 403) to avoid existence leakage. Approval mutations use the customer-keyed wrappers in approvalWorkflow (load row → resolve owner → reject NULL/mismatch → call primitive).\n\nFAIL-CLOSED DEFAULTS: no session → login; mismatched/NULL customer for a non-staff user → 404/403, never a silent empty result. The public free-diagnostic widget (demo/lead-scoped) and the signed weekly-report permalink are the ONLY unauthenticated surfaces; both are non-enumerable and the diagnostic writes nothing customer-private. The legacy unauthenticated Fastify GET /smr/:runId and POST /diagnose are REMOVED from public exposure (bound to internal/ops only) so the now-multi-tenant product has no unscoped report route. Defense-in-depth RLS, IF added later, is scoped ONLY to the NEW Phase-5 plain tables (app_user, app_session, subscription, invoice, report_snapshot) — NEVER the Timescale hypertables/CAGGs, whose unscoped aggregate reads the measurement core depends on must not break.

## API Layer

Next.js-owned tenant API; the Fastify engine API is NOT re-blessed as a customer surface. The dashboard's reads/mutations run in Next.js Route Handlers + Server Actions (Node runtime) so session/cookie auth and per-customer scoping live in ONE place; they call assembleReport()/repo.* directly via the server-only engine facade (apps/web/lib/engine.server.ts). The engine's Fastify process keeps /healthz and /providers for ops; the previously-public GET /smr/:runId and POST /diagnose are removed from public exposure (internal/ops binding only) because they are unscoped (review must-fix). This avoids a second customer-facing HTTP hop AND avoids a cross-process session-trust seam.\n\nREAD (Node runtime, read-only, every handler calls requireCustomerScope first):\n- GET /api/overview → latest report_snapshot KPIs + decomposition for session.customerId.\n- GET /api/reports → repo.listReportSnapshots(customerId) (trend list).\n- GET /api/reports/[snapshotId] → report_snapshot.report_json (the as-delivered RunReport) AFTER customer_id ownership check; 404 on mismatch.\n- GET /api/trends → report_snapshot history series (O(snapshots), no re-aggregation).\n- GET /api/evidence/[responseRawId] → findResponseRaw(...).answer_text after responseRaw.customer_id === session.customerId; 404 otherwise.\n- GET /api/billing → subscription + sumLlmUsageForPeriod + invoices.\nThese call assembleReport()/repo.* — never raw SQL. The RunReport that report.ts validates through the verifiableNumbersGate is the wire format (after toWireReport Date→string), so the §7 \"only verifiable numbers / no free-text claims\" guarantee extends to the UI unchanged.\n\nMUTATION (Server Actions, Node runtime, auth-gated; each: getServerSession → requireCustomerScope/requireStaff → call the EXACT engine/CLI function via a customer-keyed wrapper → revalidatePath):\n- claim sign-off → signClaimSourceForCustomer(claimId, customerId, by) + regateAsset.\n- deploy approval → approveDeployRowForCustomer(assetId, customerId, by).\n- template review/activate/edit (STAFF only) → actionReviewed/actionActive/actionEdit.\n- subscription cancel-at-period-end → repo.cancelAtPeriodEnd(customerId).\nNo mutation re-implements logic; all are thin auth+identity+ownership wrappers. The public diagnostic Server Action is rate-limited + per-IP/day cost-capped and scoped to the demo/lead customer.

## Key Decisions

- **apps/web/ Next.js + npm workspaces, IMPORTING @engine/domain/* verbatim via tsconfig path alias; documented as an amended Phase-0 decision** — Phase 0 chose TS specifically so the dashboard shares domain zod/types; workspaces+alias add zero new infra and keep the single src/ tree as the engine, honoring DESIGN.md 'no heavy monorepo tooling' while satisfying the hard constraint to not duplicate types.
- **Enforce the client/server bundle boundary with React 'server-only' on a web-side engine facade (engine.server.ts), not just an ESLint rule** — @engine/* aliases the whole src/ tree which includes pg/kysely/pino modules; a stray client import would ship server code. 'server-only' makes that a build-time error by construction; ESLint is defense-in-depth. Only @engine/domain/* (types) may cross to client components.
- **Reads go through tenant-scoped Next.js handlers calling assembleReport()/repo.* after a server-side ownership check; REMOVE public GET /smr/:runId and POST /diagnose from the Fastify engine** — assembleReport(runId) is not customer-scoped and the legacy /smr/:runId is unauthenticated — in a multi-tenant product any caller could fetch any tenant's RunReport by iterating runIds. Ownership is checked via findRun(runId).customer_id===session.customerId with 404 on mismatch (no existence leak).
- **Add customer-keyed wrapper repo fns (signClaimSourceForCustomer, approveDeployRowForCustomer) that resolve the row owner and fail-closed BEFORE calling the Phase-0 primitive** — signClaimSource(id)/approveDeployRow(assetId) are id-keyed with no customer predicate; content_deploy_queue has no customer_id and content_asset.customer_id is NULLABLE. A narrated 'route checks ownership' over functions that structurally cannot is fail-open; the wrapper + cross-tenant 404 test makes it fail-closed and tested.
- **Move §5.5 template review/activate to a STAFF-ONLY console; keep only claim sign-off + deploy approval in the per-customer dashboard** — industry_template has NO customer_id, is shared per-industry, and actionActive() demotes the industry's active row AND emits YAML via materialize()+loadTemplate. A customer owner activating it mutates global state for other customers — it must be staff-only, stamped with the staff email for §12 audit.
- **Persist an IMMUTABLE report_snapshot at delivery time; trends read snapshots, not live assembleReport** — report.ts recomputes from current_judgment, so a re-judge after delivery would silently change the historical email vs the trend chart. Freezing report_json as 'as delivered' keeps the emailed numbers immutable and trends O(snapshots); the UI labels snapshots 'as delivered'.
- **report.deliver = at-least-once + idempotent (singletonKey report:runId + report_delivery UNIQUE + report_snapshot UNIQUE(run_id)); boot catch-up enqueues for completed runs lacking a snapshot; ship one REAL delivery sink** — cycle.aggregate is a retryable handler that may commit before enqueue, so a singletonKey alone prevents double-send but not a MISSED send. Idempotent send + catch-up recovers misses. A console NoopSink alone is not 'weekly report automation' — the §10 retention loop needs a working Resend/SMTP sink.
- **WoW delta uses findPreviousOperatingRun filtered to kind='operating' AND status='completed'** — run.status includes failed/over_budget/partial with different n_total snapshots; a naive 'previous run' would mislead the headline week-over-week delta that drives the email and Overview.
- **Billing separates our llm_call USD cost from customer KRW price: pure pricing.ts (∝ questions×languages) for the base, with margin+FX+VAT layered in invoice_line; NULL-customer llm_call spend absorbed as overhead** — llm_call.usd is our (tiny, Gemini-only, pre-VAT, USD) provider cost, not a price; metering invoices off it under-bills and ignores §1 'VAT 별도'. llm_call.customer_id is NULLABLE (onboarding/diagnostic), so that spend can't be attributed and is explicitly absorbed, not silently dropped into a tenant invoice.
- **NO Postgres RLS on Timescale hypertables/CAGGs; app-layer requireCustomerScope is the primary, tested tenancy guard; app_user.customer_id is NULLABLE for staff** — RLS on response_raw/mention_judgment/llm_call/cost_daily can break CAGG refresh, compression, and the §11 budget reads (the measurement core's aggregate reads are unscoped) — violating 'do not touch the measurement core'. A NOT NULL app_user.customer_id can't model cross-customer ops; a CHECK enforces non-staff must be scoped while staff may be NULL.
- **Dark navy + cyan visual system (gpto.kr's verified actual mode), Pretendard + tabular-nums, Recharts, with §0/§1 honesty as always-visible tested components** — The reviews verified gpto.kr is DARK mode with cyan accents — a light system is the inverse of the reference. §0 'no results guaranteed' and §1 'month-to-month, cancel anytime' are contractual and rendered as persistent footnotes on the diagnostic, weekly report, and billing screens, not dismissible toasts.
- **Cross-process Date serialization handled by a toWireReport(Date->ISO string) transform; client components only receive WireRunReport** — RunReport.generatedAt and run timestamps are JS Date; passing a Date across the RSC->client boundary serializes to a string while the shared type still declares Date, so charts/tables would mismatch. An explicit wire DTO keeps the shared type honest about the runtime shape.
